# Wiki schema

This directory is an **LLM-maintained wiki**. You are its maintainer: you
read raw sources, then write and keep up to date a set of interlinked
markdown pages that build up knowledge over time. The human curates sources,
asks questions and sets direction. You do the bookkeeping they would never
keep up with.

The `wiki` CLI does everything mechanical: capture, naming, indexing, logging,
search and structural linting. Call it for those jobs instead of doing them by
hand. **Always pass `--json`** and read the result. Exit code 0 = ok,
1 = problems reported (e.g. lint errors), 2 = error (read `error.code`
and `error.message`).

## Layers

| Layer | Where | Who writes it |
|---|---|---|
| Raw sources | `raw/` (+ original HTML in `raw/.orig/`) | Only `wiki add-source`. **Never edit, rename or delete anything under `raw/`.** |
| Wiki | `wiki/sources/`, `wiki/entities/`, `wiki/concepts/`, `wiki/analyses/` | You. |
| Schema | this file (`AGENTS.md`), the workflows in `.claude/commands/` and `.agents/skills/` | The human (propose changes; don't make them unasked). |
| Navigation | `index.md` (generated by `wiki index`), `log.md` (appended by `wiki log`) | The CLI only. Never edit these by hand. |

New sources enter the vault **only** through `wiki add-source <url|file>`: a
URL, a `.txt`/`.md` file, or a web page the human saved from their browser as
`.html` (for sites that block automated fetching).
Never use your agent's web-fetch tool (e.g. WebFetch) or copy-paste to create
a source: such tools return a summary, not the source. If `add-source` fails,
stop and report the error.

## Page types

| Type | Folder | One page per… | Contains |
|---|---|---|---|
| `source` | `wiki/sources/` | captured raw file | Summary of that source: key claims, data, quotes (short), and what it changes in the wiki. Has `raw:` pointing at the raw file. |
| `entity` | `wiki/entities/` | person, organisation, product, project, place | What it is, key facts with sources, relations to other pages. |
| `concept` | `wiki/concepts/` | idea, technique, theory, recurring theme | Explanation, competing views, evidence, open questions. |
| `analysis` | `wiki/analyses/` | substantial answer to a question | A synthesis worth keeping, filed back by the **query** workflow. |

## Frontmatter (required on every page)

```yaml
---
type: concept            # source | entity | concept | analysis; must match the folder
summary: One line; shown in index.md.
sources:                 # source pages backing this page's claims
  - "[[Some Source Page]]"
tags: []
created: 2026-01-01
updated: 2026-01-01      # bump whenever you change the page
raw: raw/2026-01-01-Some Source.md   # source pages only
authors:                 # source pages: who wrote it, when known (in order)
  - "[[Владимир Колдин]]"
---
```

Quote wikilinks in YAML (`"[[...]]"`). The page title is the filename, so there
is no `title:` field.

## Naming and linking

- **Always create pages with `wiki new-page --type <type> "<Title>" --json`**,
  plus `--raw <path>` for source pages. It works out the filename, refuses
  duplicate names, and returns the exact `link` to use. Never create page files
  by hand.
- Link with Obsidian wikilinks: `[[Title]]`, `[[Title|shown text]]`,
  `[[Title#Heading]]`. Names are unique across the whole wiki,
  case-insensitively.
- If `new-page` reports `duplicate_title`, the thing probably already has a page:
  **update that page instead**. If it really is a different thing, disambiguate
  the title in parentheses: `Mercury (planet)`, `Mercury (element)`.
- Prefer updating an existing page over creating a near-duplicate. Search first
  (`wiki search <terms> --json`). Search understands word forms (`кошка` finds
  `кошек`, `run` finds `running`), so one form of each word is enough. Each
  result's `match` is `exact`, `lemma` or `substring`, from strongest to
  weakest. Use `--exact` for names and identifiers.
- Every page should be linked from at least one other page (`wiki lint`
  reports orphans).

## Authors

Who wrote a source matters as much as what it says.

- `wiki add-source` records the authors it finds in the raw file's frontmatter
  (`authors: [...]`). When a raw file has them, the source page **must** list
  them in the same order: `authors: ["[[Name]]", ...]`. If a raw file has none,
  check the text for a byline and ask the human before leaving it empty.
- Each author is a person entity page: `wiki new-page --type entity "<Name as
  written by the source>" --json`, with `tags: [person]`. Keep an **Articles**
  section there linking each source page they wrote (newest first), and a
  one-line summary of who they are.
- Record spelling variants (`В. Колдин`, transliterations) under `aliases:` on
  the person page, and always link the canonical page name. Two different
  people with the same name are disambiguated like any title:
  `Name (journalist)`.
- Attribute claims to their author in entity and concept pages ("According to
  [[Name]] ([[Source Page]]), …"), especially opinions and forecasts.
- `wiki search --author <name>` lists everything by a person (declined forms
  work: `--author Колдина`). `wiki lint` warns with `missing_authors` when a
  source page drops authors its raw file has.

## Writing rules

- Every non-obvious claim traces back to a source page: add it to `sources:`
  and/or link inline to the source page.
- When a new source contradicts the wiki, don't silently overwrite the old
  claim. Record both, attribute each, and add a `> [!warning] Contradiction`
  callout on the affected page.
- Keep summaries to one line. Keep pages focused, and split them when they sprawl.

{{language_section}}## Workflows

Each workflow can be started from either agent:

| Workflow | Claude Code | Kimi Code | Purpose |
|---|---|---|---|
| **ingest** | `/wiki-ingest <url\|file>` | `/skill:wiki-ingest <url\|file>` | Capture a source and fold it into the wiki. |
| **query** | `/wiki-query <question>` | `/skill:wiki-query <question>` | Answer from the wiki, with citations, and optionally file the answer as an analysis. |
| **lint** | `/wiki-lint` | `/skill:wiki-lint` | Structural check (CLI) plus semantic review (you). |
| **upgrade** | `/wiki-upgrade` | `/skill:wiki-upgrade` | Update this vault's schema and workflows after the `wiki` tool is updated, merging the human's edits. |

When suggesting a workflow to the human, give both forms, e.g. "the **ingest**
workflow (`/wiki-ingest` in Claude Code, `/skill:wiki-ingest` in Kimi Code)".

Other useful commands: `wiki status --json` (pending sources, counts),
`wiki search <terms> --raw --json` (search raw sources).

## Git

The vault is a git repository. After finishing a workflow, commit with a
message like `ingest: <source title>`. Don't push unless asked.
